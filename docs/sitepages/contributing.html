Contributing

The tool is open source. Bug reports, model corrections and documentation fixes are all welcome, and the calculation engine is a separate project that takes contributions of its own.

WhatWhere
Application sourcegithub.com/FedericoTartarini/comfort-tool
Calculation enginejsthermalcomfort
Live toolcomfort.cbe.berkeley.edu

Reporting a bug

File it on the application repository's issue tracker. Help lists what to include in short, a share link reproducing the case is worth more than any description of it.

One decision to make first: is it the interface or the engine? The application selects inputs, presents results and draws charts. It contains no copy of the model equations every number comes from jsthermalcomfort. A wrong value for valid inputs usually belongs on the engine's tracker; a wrong label, band, unit conversion or control belongs here.

Setting up

You need Node.js 22 or later, npm, and git. The engine is vendored as a git submodule, so clone recursively:

git clone --recurse-submodules <repo-url>
cd comfort-tool
npm install
npm run dev

There is nothing to install by hand. npm install initialises the submodule, installs its dependencies and compiles it including if you cloned without --recurse-submodules.

Working on the engine

The engine is a fork of jsthermalcomfort at vendor/jsthermalcomfort. Edit it in place, then rebuild so the app picks up the change:

npm run build --prefix vendor/jsthermalcomfort

It has its own test suite, deliberately excluded from the application's tests:

npm test --prefix vendor/jsthermalcomfort

Commit and push engine changes inside the submodule first, then commit the updated submodule pointer in the application repository. A pointer bump without the pushed commit behind it leaves a repository nobody else can build.

To pull a fork commit someone else pushed:

git submodule update --remote vendor/jsthermalcomfort
npm run build --prefix vendor/jsthermalcomfort

Before you open a pull request

Run the full validation suite:

npm test
npm run check
npm run lint
npm run build
npm run test:visual
git diff --check

The visual suite needs its browser installed once:

npx playwright install chromium

Visual baselines

Approved baseline images live beside the Playwright tests. Update them only for a change that is meant to be visible, with npm run test:visual:update, and look at every expected, actual and diff image before committing. A baseline refreshed without being inspected turns the visual suite from a safety net into a rubber stamp.

Adding a model

Each registered model has one focused declaration under src/declarations/, which owns its identity, inputs, options, zones, calculation, result rows, charts and modifiers. The repository has a developer guide for the whole path see docs/adding-a-model.md in the source tree.

Some invariants worth knowing before you start:

  • Units. Shared inputs, modifier values and editable chart bands are stored canonically in SI. src/engines/units/ is the only place conversion happens.
  • Base inputs stay separate from modifier configuration. Effective inputs are derived through the modifier chain, never written back over what the user typed.
  • Options are complete and exact. Parsers reject missing, extra or illegal values rather than silently defaulting.
  • Charts are declared per model. There is no shared chart set, and no parallel chart-id tree beside the declaration.
  • Presentation-only changes never invalidate a calculation cache this is what lets Explore's editable bands be presentational without touching results.
  • Direct jsthermalcomfort imports stay inside the declaration and engine layers.

A new model also needs documentation: a model page answering the same questions in the same order as the existing ones, an entry in References and citations, and rows in the model tables on the home page.

Documentation

Two separate things share the word:

  • These pages the user documentation you are reading.
  • The Markdown under docs/ in the source tree an internal developer reference (architecture, adding a model, testing). It is maintained in the repository, is not generated, and is not part of the production build.

If you change behaviour a user can see, the user documentation needs updating in the same pull request. A band boundary, an input range or a control that is documented but no longer true is worse than one that was never documented at all.

When you document a band boundary or a validity limit, cite the standard or publication it comes from. If you cannot find one, say so explicitly and mark it tool-specific see the list at the foot of References and citations. Do not attach a plausible-looking citation to a number you could not trace.

Citing the tool

If you use it in published work, cite the software paper the exact reference is on References and citations.
